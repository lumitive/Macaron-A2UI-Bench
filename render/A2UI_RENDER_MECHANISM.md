# A2UI 渲染机制说明

## 目的

本文档说明 A2UI 视觉评测链路中的渲染机制，重点介绍核心方法和运行流程，不涉及具体代码文件位置。

这里的 render 阶段并不是重新生成 UI，而是把已经存在的 A2UI 消息序列稳定地还原成真实可见的界面截图，供人工检查或视觉模型打分使用。

## 整体流程

这条渲染链路本质上是一个“重放系统”，不是一个“生成系统”。

整体步骤如下：

1. 读取已有模型输出中的 `a2ui_messages`。
2. 过滤掉明显不可渲染的样本。
3. 通过 URL 参数把 A2UI 消息序列发送给本地网页渲染器。
4. 由 Flutter Web 页面重建并展示该 UI。
5. 等待页面明确报告“渲染完成”。
6. 使用 Playwright 截图。
7. 裁掉多余页面背景，只保留真正的 UI 区域。
8. 将截图交给后续视觉评测模块。

这个设计的关键点在于：渲染阶段只是对消息协议做确定性重放，而不是再次调用模型。

## 输入约定

渲染器接收的是一个 A2UI 消息数组。数组中的每个元素都是协议层面的消息，例如：

- `beginRendering`
- `surfaceUpdate`
- `dataModelUpdate`
- `deleteSurface`

其中最关键的是 `surfaceUpdate`，因为它定义了组件树。`dataModelUpdate` 提供组件绑定的数据状态。`beginRendering` 用来建立目标 surface。`deleteSurface` 用来销毁 surface，主要和生命周期完整性有关。

在这个评测流程里，通常要求一次响应只对应一个 surface。多 surface 输出会被视为不适合当前视觉评测流程，因为视觉评测默认每个样本只对应一个连贯的界面。

## 可渲染性检查

在真正调用浏览器之前，系统会先做一轮轻量的 renderability check。它的目标不是保证 UI 一定好看，而是尽量提前排除那些高度可能导致渲染崩溃、协议不合法或结构明显错误的样本。

常见检查包括：

- 是否只使用了一个 surface ID
- `dataModelUpdate` 是否带有必要字段，例如 `path`
- 组件数组是否结构正常
- 选择类组件的状态绑定形状是否正确
- 是否存在已知容易导致运行时异常的布局组合

这一层的作用是守门。它的意义在于减少无效浏览器调用，并把“协议错误”与“视觉质量差”这两类问题分开。

## Flutter 渲染服务

渲染器本体是一个本地运行的 Flutter Web 应用。整个视觉评测流程默认这个本地服务已经启动，并通过本地 HTTP 地址提供访问。

这个服务的职责很明确：

- 从浏览器 URL 中接收序列化后的 A2UI 载荷
- 将其解析成消息数组
- 确定目标 surface ID
- 在内存中按顺序重放消息流
- 把最终 surface 渲染成正常的 Flutter Widget 树

这个设计有两个重要含义：

- 渲染器本质上是一个协议消费者，而不是为每个任务单独写的页面
- 同一个渲染器可以反复复用，因为每个样本的差异只体现在传入的消息序列

## Flutter 页面如何接收数据

截图页面主要依赖 URL query 参数驱动。

最核心的参数是：

- `a2ui`：完整序列化后的 A2UI 消息数组

此外还会带一些展示控制参数，例如：

- 渲染舞台宽度
- 渲染舞台最大高度
- 页面外层 padding
- 可选的显式 surface ID

这意味着渲染页面不需要再去请求额外的后端接口来重建 UI。单个样本所需的核心界面信息已经全部打包进 URL 里了。

## Flutter 如何重建 UI

进入 Flutter 页面之后，A2UI 消息数组会被逐条重放到一个 A2UI message processor 中。

概念上，这个过程是：

1. 解析 JSON 数组
2. 把每个 JSON 对象转换成类型化的 A2UI message
3. 将每条 message 送入消息处理器，维护 surface 的当前状态
4. 由 surface host widget 根据最终状态渲染界面

消息处理器负责执行协议语义：

- `beginRendering`：创建或初始化一个 surface
- `surfaceUpdate`：定义或更新组件树
- `dataModelUpdate`：更新组件绑定的数据状态
- `deleteSurface`：清空该 surface

最终可见的结果，就是一个由这些消息重放得到的 Flutter Widget 树。

## Ready 信号机制

浏览器自动化层不会靠猜测判断“什么时候渲染完了”，而是由 Flutter 页面主动向 DOM 写入渲染状态。

常见状态有三种：

- `loading`
- `ready`
- `error`

这一步非常关键，因为从浏览器视角看，Flutter Web 的初始化和渲染是异步的。如果没有显式 ready 信号，截图很容易发生在页面尚未稳定的时候，导致截到半成品或出现随机波动。

因此，截图逻辑会明确等待页面报告 `ready` 后再执行。

## 为什么使用 Playwright

Playwright 在这里承担的是“浏览器级截图引擎”的角色，而不是渲染器本身。

使用它的原因主要有：

- 它运行在真实浏览器环境里
- 可以设置稳定的等待条件
- 可以精确控制 viewport
- 可以可靠地生成 full-page 截图

在执行时，Playwright 会访问本地 render 页面，等待 Flutter 写入 ready 状态，再额外给一点短暂稳定时间，然后捕获页面截图。

Playwright 并不理解 A2UI 协议，它只负责：

- 打开页面
- 等页面进入 ready 状态
- 生成截图

这层分工很重要：

- Flutter 负责“把消息正确渲染出来”
- Playwright 负责“把已经渲染好的页面稳定截下来”

## Viewport 与 Stage 的区别

在这个机制里，通常会同时控制两类尺寸：

- 浏览器 viewport 尺寸
- 页面内部渲染 stage 尺寸

viewport 决定浏览器截图时的可视窗口大小。

stage 决定页面内部 UI 预览区域允许占用的宽高范围。

这两个概念分开设计很有必要，因为：

- 很长的 UI 需要较高的浏览器页面才能完整截取
- 卡片式或窄屏 UI 仍然需要被限制在合理的渲染宽度里
- 评测时希望不同样本的构图尽可能一致

实际运行时，一般会抓 full-page，但 UI 本身只会出现在一个受控大小的预览舞台内。

## 截图后的裁剪

截图完成后，系统通常还会执行一次裁剪。

原因是 full-page 截图经常会包含大量与任务无关的背景区域，特别是当 UI 本身比较短或者比较紧凑的时候，这些空白区域会非常多。

裁剪的基本思路是：

- 先估计页面背景色
- 再找到所有非背景像素的包围盒
- 把外层大面积空白区域裁掉
- 但保留一个小边距，避免把边框或阴影切掉

这样做的好处是，最终图片会更聚焦于实际 UI，本身也更适合后续视觉模型评判。

## 常见失败模式

这个渲染机制常见的失败点大致有以下几类。

### 本地渲染服务没有启动

如果本地 Flutter Web 服务没起来，浏览器就无法访问 render 页面，截图通常会很快失败。

### 载荷能解析，但运行时无法渲染

有些 A2UI 数据在 JSON 层面合法，但在重放或组件构建过程中会出错。这种情况下，页面会从 `loading` 进入 `error`，而不会进入 `ready`。

### A2UI 结构形式上合法，但协议上不合理

有些输出可以通过 JSON 解析，但仍然违背了协议预期。理论上这类问题应该尽可能在 renderability check 阶段拦下，但仍然可能有一部分在页面里才暴露。

### 技术上可渲染，但视觉质量很差

这类情况不是渲染失败。截图可以生成，但画面可能出现裁切、溢出、层级混乱、交互不清晰等问题。这些问题属于视觉评测阶段需要识别的缺陷，而不是 renderability checker 要处理的错误。

## 渲染与视觉打分的关系

渲染阶段和评分阶段是分开的。

渲染阶段的职责是：

- 尽可能忠实地重建 UI
- 稳定地产生截图
- 清楚暴露协议错误和渲染错误

视觉打分阶段的职责是：

- 检查截图
- 评估视觉完整性
- 评估任务匹配度
- 评估操作清晰度

截图就是这两个阶段之间的契约。一旦截图生成，后续视觉评测就不再依赖 Flutter 运行时本身。

## 这种设计为什么有效

这个渲染机制有效，主要因为它把职责切分得比较干净。

- 模型输出只生成一次，之后可以反复重放
- Flutter 扮演 A2UI 协议的规范渲染器
- Playwright 提供稳定的浏览器级截图能力
- 视觉评测真正评的是用户最终能看到的界面，而不是只看 JSON 是否“看起来合理”

因此，这套流程有一个很重要的性质：

一个样本只有在“能够被真实渲染出来”并且“渲染结果视觉上也成立”的前提下，才会拿到较好的视觉评估结果。

## 简要总结

这套 render 机制本质上是一个本地重放式可视化流水线：

- 将 A2UI 消息数组编码进浏览器 URL
- 由 Flutter Web 页面解析并重放消息流
- 页面通过 DOM 显式暴露 ready 状态
- Playwright 等待 ready 后截图
- 截图经过裁剪后交给后续视觉评测模块

它的核心思想不是检查“模型有没有输出一个结构上像样的 JSON”，而是检查“这份输出在真实渲染之后，用户到底会看到什么”。
